# Data API 권한: 새 테이블·격리 복원 확인

2026-10-21 기준. [Supabase 공식 변경 안내](https://github.com/orgs/supabase/discussions/45329)에 따르면 2026-10-30부터 기존 프로젝트에서도 새 `public` 테이블에 자동 Data API 권한이 부여되지 않는다. **기존 테이블의 권한을 일괄 회수하는 변경은 아니다.** 테이블 접근 권한(GRANT)과 행 접근 제어(RLS)는 별도이며 둘 다 확인한다. 운영 DB나 프로젝트 보안 설정을 이 문서만 보고 변경하지 않는다.

## 1. 새 테이블을 만드는 코드

- `CREATE TABLE`에는 스키마를 명시한다. API에서 사용할 테이블은 같은 마이그레이션에 최소한의 명시적 GRANT, RLS 활성화, 정책을 함께 둔다. RPC 전용 테이블에는 직접 클라이언트 접근을 주지 않는다.
- `tests/fixtures/data-api-table-contracts.json`에 생성 시점의 `anon`, `authenticated`, `service_role` DML 권한과 목적을 기록한다. 빈 목록은 **그 생성 파일에 명시적 DML 권한이 없다는 뜻**이며 운영 권한 실측 결과가 아니다. 새 계약을 현재 코드에서 자동 생성해 무검토 승인하지 않는다.
- 소유자 열 변경 금지처럼 열 단위 권한도 계약에 포함한다. 시퀀스가 필요한 INSERT, 함수 EXECUTE, 스키마 USAGE, 뷰의 `security_invoker` 및 RLS 정책은 별도 실제 SQL/클라이언트 시험에 포함한다. 테이블 GRANT 하나로 이들이 검증되지는 않는다.
- 신규 공개 테이블은 계약과 역할별 동작 시험을 추가한다. `ALTER DEFAULT PRIVILEGES ... GRANT`나 `GRANT ... ON ALL TABLES`로 오류를 덮지 않는다. `42501`이 나면 필요한 역할·객체·연산부터 확인하고 의도된 차단인지 판정한다.
- 수정 후 `npm --prefix tests ci --ignore-scripts`, `npm --prefix tests run test:data-api`를 실행한다. 이 검사는 기본 단위검사와 별도 CI 작업에도 연결돼 있다.

### 자동 검사의 범위

1. 생성 계약 검사는 저장소 마이그레이션의 최상위 `CREATE TABLE`을 조사하고, 같은 파일의 명시적 테이블/열 DML GRANT·REVOKE와 RLS 활성화를 검증한다. 현재 16개 public 테이블의 **과거 생성 계약**이며, 나중에 폐지된 기능을 다시 노출하라는 지시가 아니다.
2. 제한된 SQL 문법 검사이므로 완전한 PostgreSQL 파서가 아니다. 주석·문자열·함수/DO 본문 속 SQL은 실행하지도 권한 선언으로 인정하지도 않는다. 동적 테이블 생성, 상속/파티션, 별도 노출 스키마, 역할 상속, 이후 마이그레이션의 전체 ACL 변화는 수동 검토와 실제 재생 시험이 필요하다. 지원하지 않는 문법을 무시하도록 검사를 느슨하게 바꾸지 않는다.
3. PGlite 시험은 자동 테이블 GRANT가 없는 임시 DB에 실제 사진/DonFlow/게시판 생성 SQL과 관련 후속 SQL을 재생한다. 대상 테이블 권한은 테스트가 보충하지 않는다. 인증·Storage 기반 스키마와 보조 함수, 이전 게시판 원본, 무관한 폐지 대상은 가상 fixture다. 실제 회원·파일·접속정보를 쓰지 않는다.
4. 이는 **운영 DB 상태, 전체 초기 스키마 재생, 실제 백업의 ACL 포함 여부, PostgREST/GraphQL/JWT/Storage API 통합, 전체 서비스 복구 완료를 증명하지 않는다.** 기존의 파일 해시/암호화 복구 검사와 서로 대체할 수 없다.

### 선택 실행: 실제 로컬 HTTP API

- `node tests/data-api-http-access.test.cjs --check-guards`는 서비스 없이 loopback·실행 동의·비밀값 오류 숨김 안전장치만 검사한다.
- `.github/workflows/data-api-http.yml`은 승인된 동일 저장소 시험 브랜치 또는 명시적인 수동 입력에서만 실행한다. 표준 Ubuntu 24.04 runner의 새 로컬 Supabase native stack에 가상 계정과 데이터만 만들며 운영 Secret·hosted 프로젝트를 사용하지 않는다.
- 실행기는 공식 CLI v2.121.0의 고정 SHA-256을 검사하고 `api.auto_expose_new_tables=false`로 시작한다. 실제 Auth 로그인 JWT로 PostgREST와 Storage를 시험하고, 실패 시에도 프로세스 종료·포트 닫힘을 확인한다. 원시 로그·키·세션은 공개 로그나 artifact로 올리지 않는다.
- 독립 실행은 쓰기 가능한 실제 OS 홈과 Node 20+, Python 3, psql, curl, tar가 있는 승인된 임시 환경에서 `OJJUDA_LOCAL_API_TEST=1 RUNNER_TEMP=/승인된/임시경로 bash tests/run-data-api-http.sh`를 쓴다. 기존 시험 폴더를 재사용하지 않으며 CLI 포트 registry 경로의 접근 제한을 우회하지 않는다.
- HTTP 시험도 합성 기반 스키마 위의 지정 마이그레이션만 다룬다. 익명 가입 계정은 PGlite 시험 범위이며, 전체 백업 ACL·실제 hosted 환경·전체 서비스 복원 검증은 여전히 별도다. 실제 실행 결과는 해당 CI run에서 확인하며 안전장치 검사 통과만으로 API 성공이라 하지 않는다.

## 2. 현재 기능을 기준으로 하는 역할별 확인표

실제 격리 환경에서 비로그인(anon), 일반 회원 A/B(서로 다른 계정), 필요한 경우 관리자·미성년/생년 미확인·익명 가입 계정을 준비한다. 역할만 바꾼 관리자 접속이 아니라 실제 테스트 계정의 세션으로 Data API를 호출한다. `service_role`로 성공한 요청을 일반 회원 성공으로 기록하지 않는다. 토큰은 로그·PR·스크린샷에 남기지 않는다.

| 대상 | 허용할 동작 | 반드시 차단/제한할 동작 |
| --- | --- | --- |
| 사진 목록·원본 | 자격 있는 소유자의 자기 사진, 승인된 전체공개 사진, 수락된 친구에게만 친구공개 사진 | 비로그인·미성년·생년 미확인·익명 가입자의 사진/원본 열람, 타인의 비공개/승인대기 사진 |
| 사진 생성·관리 | 자격 있는 A의 자기 경로 업로드/생성/삭제, 실제 관리자 승인 | B가 A로 가장한 생성, B의 A 비공개 사진 변경·삭제, 일반 회원의 승인·관리자 명단 수정 |
| 사진 신고 | 권한 있는 회원의 신고 RPC | 직접 `photo_reports` 읽기/쓰기, 비로그인 신고 RPC, 접근 불가한 비공개 사진 신고 |
| DonFlow (폐지된 기능) | 기존 호환 읽기에서 A/B 데이터가 서로 섞이지 않음 | 비로그인 직접 접근, INSERT/UPDATE/DELETE 및 `life_donflow_save` RPC (열 단위 UPDATE 포함) |
| 게시판 댓글 (폐지된 기능) | 기존 호환 읽기가 원글 공개 범위·차단 관계를 지킴 | 비로그인 직접 접근, 현재 INSERT/DELETE/UPDATE, B가 A의 댓글인 것처럼 쓰기 |

사진의 제한은 `20261006021326_photo_ttang_adult_access.sql` 등 후속 마이그레이션을 포함한 현재 정책으로 판단한다. 최초 생성 파일에 anon SELECT가 있다는 이유로 실제 익명 열람을 허용하면 안 된다. DonFlow와 게시판 댓글은 `20261020200500_retire_unused_world_data.sql`에서 폐지됐으므로 과거 쓰기 기능을 다시 열어 검사를 통과시키면 안 된다.

조회 차단은 SQL 오류뿐 아니라 성공 응답의 빈 배열로 나타날 수 있다. UPDATE/DELETE도 권한 오류 또는 영향 행 0일 수 있으므로 응답 코드만 보지 말고 실제 행·파일이 바뀌지 않았는지 확인한다. 허용 요청은 예상 행/바이트와 소유권까지 확인한다.

### 열 권한 회수 주의

PostgreSQL에서 테이블 수준 REVOKE는 해당 열 권한도 회수한다. 반대로 테이블 전체 권한을 가진 역할에서 특정 열 권한만 회수해도 전체 권한이 남으면 차단되지 않는다. 현재 로컬 재생 시험은 DonFlow의 과거 열 단위 UPDATE 권한도 회수됐음을 확인한다. 실제 복원본에서는 `has_column_privilege` 등으로 유효 권한을 다시 확인하고, PUBLIC/역할 상속을 포함한 다른 권한 경로도 검토한다. 의도와 다른 잔여 권한은 임의로 운영에서 수정하지 말고 좁은 수정안과 적용 승인을 준비한다.

## 3. 실제 백업·복원 공개 전 승인 단계

1. 책임자, 허용된 격리 프로젝트, 비용/환경 생성 권한을 먼저 확인한다. 운영 프로젝트 URL/ref를 대상에 넣지 않는다. 승인 없이 새 프로젝트·영구 키·보안 설정을 만들거나 변경하지 않는다.
2. 관리자가 안전한 환경에서 백업의 `roles.sql`, `schema.sql`에 대상 GRANT/REVOKE 및 열 ACL이 들어 있는지 확인한다. CLI 명령을 사용했다는 사실만으로 권한 보존을 단정하지 않는다. 실제 개인정보가 든 덤프를 저장소/CI/공개 PR에 올리지 않는다.
3. [RECOVERY.md](RECOVERY.md)의 격리 복원 절차대로 역할→스키마→데이터를 복원한다. 오류를 무시하지 않는다. 자동 권한 부여가 없는 새 환경의 기본값을 확인하고, 실제 복원 결과의 객체·역할·RLS·정책·열 권한을 원본의 의도와 대조한다. 덤프의 오래된 기본 GRANT가 의도치 않게 복원되는지도 검토한다.
4. 위 표를 실제 Data API와 Storage API에서 확인한다. 실제 백업에 남은 개인정보 대신 승인된 테스트 계정/가상 행으로 경계 시험을 한다. 데이터를 외부로 복사하는 행위나 테스트용 계정/행 생성도 해당 환경의 허용 범위 안에서 수행한다.
5. 결과에는 대상 환경 식별자, 커밋/마이그레이션 목록, 실행 일시, 계정 역할(토큰 제외), 요청 연산, 예상/실제 결과, 변하지 않아야 하는 행/파일 검증을 기록한다. 성공/실패/미실행을 구분한다.
6. 모든 허용·차단 동작을 확인하고, 탈퇴/삭제 자료 재등장 방지 등 기존 복구 조건까지 충족한 뒤에만 공개한다. 여기까지의 성공도 병합·배포 승인을 대신하지 않는다.

## 안전한 중단 조건

- 예상보다 넓은 열람/쓰기, 필요한 명시적 GRANT 누락, 실제 덤프 ACL 불명, 테스트 환경 미승인, 토큰 노출 위험이면 공개/다음 배포를 중단하고 책임자에게 확인한다.
- 기존 테이블에 10월 30일이 지났다는 이유만으로 전체 GRANT를 추가하지 않는다. 문제의 정확한 역할·객체·연산을 좁히고 필요한 변경만 검토한다.

참고: [Supabase Data API 보안](https://supabase.com/docs/guides/api/securing-your-api), [PostgreSQL REVOKE](https://www.postgresql.org/docs/current/sql-revoke.html).
