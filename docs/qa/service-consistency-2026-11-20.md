2026-11-20 · 기준 소스 `1a8366b` · 게임 릴리스 `20261120-service-actions2`

## 반영 내용

- 대전방·종료창의 나가기/취소는 왼쪽, 시작/재시작/계속하기는 오른쪽에 배치한다. 실제 DOM도 같은 순서이며 모바일에서 두 동작의 좌우 관계를 유지한다.
- 공통 결과에 `exit`, `secondary`, `primary` 역할을 명시할 수 있게 했다. 기존 단계 선택의 이전·현재·다음 순서와 단일 결과 확인은 유지한다.
- 원카드, 윷놀이, 뱅, 포커, 탱크, 맞고, 마블, 술게임의 별도 화면도 같은 기준으로 정리했다. 공통 방 목록과 장기 참여창의 취소/참여 순서도 일치시켰다.
- 기존 버튼 콜백, 방장·참가자 권한, 점수·정산, 비동기 잠금·실패 재시도를 유지했다. 맞고 시작 버튼의 실제 사용자 입력 확인도 유지했다.
- 변경된 진입 HTML·모듈·공통 자산·상위 로더·동적 이동 주소의 캐시를 갱신했다. 오락실은 `1.3.4`, 영향받은 게임 39개만 각각 패치 버전을 올렸다.
- [서비스 목록](service-inventory.md)을 HTML 115개와 공개 조직의 50개 담당에 맞춰 정리했다. 가입·계정·쭈·알림·초대·복귀·자료 인계·배포·백업의 확인 기준을 포함한다.

## 발견한 운영 미완료

**외부 전체 백업이 성공한 것으로 처리하면 안 된다.** 최근 확인한 [주간 백업 작업](https://github.com/ojjuda-note/ojjuda-note.github.io/actions/runs/43644756848/job/132610359815)은 `Back up, encrypt, upload and verify` 단계에서 실패했다. 원인은 Vault 복구키 보관에 필요한 백업용 Supabase 접근 토큰이 비어 있는 상태다.

담당은 백업복구팀·서버관리팀이다. `.github/workflows/nightly-backup.yml`의 `BACKUP_SUPABASE_ACCESS_TOKEN` 설정을 준비한 뒤 같은 백업의 암호화·업로드·검증 성공을 확인하고, 별도로 복원 시험을 해야 한다. `ops/backup.py`의 보호 검사는 유지한다. 비밀값은 조회·노출하지 않았다.

임시 소스 백업 성공이나 사전 보안검사 통과는 회원 DB·원본 파일 전체 백업 또는 복원 성공을 뜻하지 않는다. 기존 운영 화면은 이 실패를 ‘백업 미완료’로 구분한다.

## 확인 범위

이 결과는 소스 연결, 격리된 검사, 실제 GitHub 작업 기록에 근거한다. 운영 회원의 가입·메시지·구매·대전·DB 변경은 하지 않았다. 인사·회계·계약·스레드·블로그 등 외부 운영자료가 필요한 업무는 책임과 확인 경로를 정리했으며, 실제 외부 업무가 모두 연결되어 정상 실행 중이라고 판정하지 않았다. 조직도에 담당이 있다는 사실은 상시 자동 점검이 실행된다는 뜻이 아니다.
