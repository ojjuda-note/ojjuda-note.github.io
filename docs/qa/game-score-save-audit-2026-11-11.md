## 운영 서버 반영과 검증

적용한 migration:

1. `20261111082841_continuous_game_score_limits.sql`: runner·screw_flat, 네 함수의 상수 8곳 수정.
2. `20261111083715_arcade_long_game_score_limits.sql`: stacker 4곳·chacha_rush 2곳, 상수 6곳 수정.

각 적용 직전·직후 `pg_get_functiondef` 전체와 권한 메타데이터를 비교해 지정한 숫자만 변경됐음을 확인했다. 보안 모드, 소유자, 실행 권한, search_path와 기존 다른 게임 상한이 그대로다. 두 migration은 재실행에 안전하며 예상과 다른 함수 정의가 있으면 전체 변경을 중단한다. 운영 사용자 점수 행은 조회하거나 수정하지 않았다.

공개·내부 RPC 계약과 관련 Edge 함수 배포 상태, 최근 로그를 읽기 전용으로 확인했다. HTTP 성공 응답만으로 실제 `ok:true` 저장을 단정하지 않았다. 최근 사용이 없는 경로는 운영 성공 사례로 계산하지 않았다.

Supabase 보안 advisory 종류·등급·건수는 전후 동일했다. 기존 advisory는 이번 점수 수정의 결과가 아니다. 참고: [보안 정의자 뷰 안내](https://supabase.com/docs/guides/database/database-linter?lint=0010_security_definer_view), [RLS 정책 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [함수 실행 권한 안내](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

GitHub 검증 중 궁수 진입 테스트의 캐시 기대값이 이전 모듈 버전을 가리키는 것을 확인해, 실제 갱신한 기록 클라이언트 버전에 맞췄다. 운영 코드의 저장 동작을 되돌리지 않았다.

## 배포와 복구의 한계

Git CLI와 GitHub CLI에는 쓰기 인증이 없어 최초에는 `AGENTS.md`의 큰 파일 전송 규칙에 따라 화면 코드 업로드를 보류했다. 이후 사용자가 이번 수정에 한해 연결된 GitHub 도구로 전송하는 것을 승인했다. 승인된 수정 파일만 전송하고 파일별 Git blob SHA를 대조한 뒤, 최신 main 변경을 보존한 PR로 통합한다. 이 예외는 저장소의 일반 전송 규칙 자체를 변경하지 않는다.

브라우저 저장소와 서버 연결이 동시에 실패하면 페이지를 유지하는 동안의 메모리 재시도는 가능하지만, 새로고침 뒤 미전송 점수의 영구 복구까지 보장하지 않는다. 저장소 읽기가 차단된 동안 접근하지 못한 과거 run의 미확정 점수도 자동 합산하지 않는다. 서로 다른 run을 더하면 중복 집계 위험이 있으므로 현재 활성 run을 유지한다. 기존에 서버로 보내지 못한 모든 과거 점수를 복구했다는 의미는 아니다.
